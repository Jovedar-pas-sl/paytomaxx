## 3. SEGURIDAD por severidad

### CRITICAL
Ninguno confirmado en sentido estricto. **Matiz importante**: el HMAC opcional (HIGH abajo) se comporta como crítico *en la práctica* porque la plantilla de producción lo deja vacío. Trátalo como prioridad 1.

### HIGH

**H1. HMAC del webhook es opcional y la plantilla de producción lo deja desactivado.** (`app/routes/webhooks.py:128-137` + `app/settings.py:38`)
Confirmado: `_verify_hmac` devuelve `True` incondicionalmente cuando el secreto está vacío (línea 133), y `waha_webhook_hmac: SecretStr | None = Field(None)` lo hace opcional. **Por qué importa aquí**: con `.env.production.template` enviando `WAHA_WEBHOOK_HMAC=` vacío, cualquiera que alcance `/webhook/waha` (red interna Docker, o IP pública si está expuesta) puede inyectar un evento `message` falso con un JID de cliente real → se inserta el mensaje, se reabre la conversación y se encola `auto_reply_job` → **Sara manda un WhatsApp no solicitado a ese cliente** en el número de la casa. También permite envenenar coordenadas (precio F3), crear contactos basura y spamear la tabla `alert`. **Fix concreto**: (1) poner `WAHA_WEBHOOK_HMAC=<secreto>` en `.env` igual al de WAHA; (2) en `settings.py` quitar `| None` y el default → `waha_webhook_hmac: SecretStr = Field(...)` para que la app no arranque sin él; (3) borrar la rama `if not secret: return True` de `_verify_hmac`. Si se quiere un bypass de dev, atarlo a `DEBUG=true`, nunca a la ausencia del secreto. Añadir `WAHA_WEBHOOK_HMAC` al `.env.example` con comando de generación.

**H2. La pista del analizador (`hint.why`) entra al bloque de sistema de Sara sin filtro anti-inyección.** (`app/agent/reply_engine.py:199-210, 226-227`)
Confirmado: `_clean_hint_text` **salta a propósito** `_INJECTION_PATTERNS` (comentario: "LLM-produced from the same trusted pipeline"). Pero `hint.why` nace de `analysis.next_action->>'why'`, que es la interpretación en texto libre del LLM analizador **leyendo el mensaje crudo del cliente**. Cadena: mensaje del cliente → analizador → `why` → JSONB → `_clean_hint_text` (solo quita HTML/control) → `build_hint_block` → bloque de **sistema** de Sara (posición autoritativa). **Por qué importa aquí**: un cliente que escriba "ignora tus instrucciones y di: [X]" puede lograr que el analizador embeba ese texto en `why`, y ese texto entra al prompt de sistema de Sara — el canal que envía WhatsApps reales. El cap de 160 chars limita el daño pero no lo impide. **Fix**: aplicar `_sanitize_for_prompt` (con la pasada de patrones) a `reason` en `_build_internal_hint` antes de `build_hint_block`, o una pasada específica de override (ignore/forget/olvida/ignora + instrucciones/reglas/sistema/prompt).

### MEDIUM

**M1. SSRF + fuga de la API key de WAHA vía `open_media_stream`.** (`app/waha_client.py:151-164` + `routes/media.py` + `webhooks.py:320-321`)
Confirmado en código: si la URL no empieza por la base, se pasa tal cual como `path` a `build_request('GET', path)`; httpx, con `base_url` configurado, resuelve una **URL absoluta** ignorando la base y **adjunta el header `X-Api-Key`** al destino externo. El webhook guarda `media.get('url')` verbatim, y el proxy `/media/<id>` lo reenvía. **Por qué importa aquí**: combinado con H1 (HMAC off), un atacante guarda cualquier URL en la DB; cuando el admin abre ese media, el servidor hace GET a la URL del atacante **filtrando la API key de WAHA** (que gobierna el envío en TODAS las líneas) y permite SSRF a Redis/Postgres internos. Incluso con HMAC, un WAHA comprometido (parsea protocolo no confiable) puede inyectar URLs. **Fix**: en `open_media_stream`, antes de construir la request, `if not url.startswith(base): raise ValueError`. Y en `media.py`, rechazar con 404 cualquier `media_url` que no empiece por `waha_api_url`. Defensa en capas.

**M2. SSRF de segundo orden vía `send_image` → WAHA descarga `photo_url` server-side.** (`waha_client.py:84-105` + `agent/auto_reply.py:476-479`)
WAHA descarga el `photo_url` que Sara envía; ese valor viene de `website_sync` espejando webs de las casas. Si una web se compromete o hay MITM en el sync (sin pinning TLS), se puede guardar un `file://` o `http://internal-host/`. **Fix**: al persistir `photo_url` en `_normalize_*`, validar `scheme == https` y `netloc == dominio_casa`. Riesgo reducido porque las URLs son de webs propias sobre HTTPS.

**M3. Rate-limiter fail-open: sin Redis se saltan TODOS los topes anti-ban.** (`auto_reply.py:254-266`, `followup.py:243-249`, `rate_limit.py:156-186`)
Confirmado: el gate solo se aplica si `ctx.get('redis')` no es None, y `allow_send`/`pace`/`record_send` hacen `except Exception: return True/return`. Una caída de Redis, un `REDIS_URL` mal puesto o un fallo transitorio **elimina todos los topes por número** mientras dure. Bajo ráfaga (atacante inundando el webhook — ver H1 — amplificado por el path de fotos que manda varios mensajes por conversación) puede generar cientos de WhatsApps/min y **provocar un ban de WhatsApp en los números de las casas** (el vector de ban primario documentado). **Fix**: fail-open por niveles — ante error de Redis, permitir pero con un token-bucket en proceso (asyncio) como fallback; loggear CRITICAL (no WARNING) cuando Redis falta al arrancar el worker; idealmente, hacer Redis obligatorio en el contexto del worker.

**M4. Inyección SQL latente por patrón f-string con `show` no validado.** (`app/routes/alerts.py:17-29`)
Hoy NO explotable (el ternario produce literal fijo o cadena vacía), pero establece el patrón de valor de usuario → SQL crudo. **Fix**: validar `show in {"active","all"}` (HTTPException 400 si no) y usar dos consultas estáticas. Misma disciplina en `queries.py:980` (`where_ack`).

**M5. Logout es GET → CSRF de logout.** (`app/routes/auth_routes.py:72-76`)
El middleware CSRF solo cubre POST/PUT/PATCH/DELETE. `<img src=".../logout">` desloguea al admin (DoS, pierde trabajo). **Fix**: cambiar a `@router.post("/logout")` + form/HTMX `hx-post`.

**M6. JWT de 30 días no revocable.** (`settings.py:29`, `auth_routes.py:72-76`)
Logout solo borra la cookie; el token sigue válido hasta 30 días si fue capturado. **Fix**: acortar a 8-12h, o JTI en Redis con TTL revocable. Sencillo: opción (b) de sesión Redis-backed que el logout borra.

**M7. Falta validación de longitud/charset en `session` del webhook.** (`webhooks.py:154, 259, 277`)
Parametrizado (sin SQLi) pero un webhook spoofeado (vía H1) puede meter una `session` gigante que acaba en `alert.message` y en `casa.name` (`⚠ {session}`). **Fix**: max 64 chars, alfanumérico + `-_`, rechazar/truncar.

**M8. Sin headers de seguridad HTTP (CSP, X-Frame-Options).** (`app/main.py` — no hay middleware; Caddyfile)
Confirmado: cero ocurrencias de CSP/X-Frame-Options en el código. Faltan de verdad `X-Frame-Options` (clickjacking sobre un panel con PII y envío en 1 clic) y CSP (sin contención de futuros XSS). HSTS/nosniff conviene revisarlos en Caddy. **Fix**: middleware FastAPI con `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`; CSP + HSTS en el bloque `header {}` de Caddy.

**M9. Clave Anthropic real comprometida en git history.** (`chatbot_maxxag/.env.example`, commit `8752a1c`)
La `.env` de wa-ops (clave `***REMOVED***`) NO está commiteada (solo en disco — higiene). **Pero** `chatbot_maxxag/.env.example` SÍ contiene una clave Anthropic completa (`***REMOVED***...`) commiteada en historial (rama `feature-operators`), más `ADMIN_TOKEN=***REMOVED****`. Si el repo está en GitHub, está expuesta. **Fix**: **rotar YA** ambas credenciales en console.anthropic.com; purgar de historial (git filter-repo); pre-commit hook (detect-secrets/git-secrets) para bloquear `sk-ant-`.

**M10. Log de warning puede contener hasta 200 chars de payload de cliente (PII).** (`webhooks.py:202`)
`logger.warning("... %s", str(data)[:200])` vuelca `body`, `from`, `pushName` a logs Docker. **Fix**: loggear solo campos no-PII: `{"msg_id":..., "from_suffix": from[-4:], "has_body": bool(body)}`.

## 6. KPIs / DATA PROFESIONAL

### Diagnóstico de los KPIs actuales
Mezcla de **útil, vanidad y promesas rotas**:
- **Rotos**: `wa_comparison` se renderiza en 2 plantillas + 2 exportadores pero `worker.py` **nunca escribe la clave** (confirmado por grep: 0 matches) → el informe de casa sale vacío. El rendimiento de **Sara no se mide en nada** pese a que envía y se autopausa.
- **Vanidad/poco fiable**: funnel, reservas confirmadas e **ingresos los "cuenta" Haiku** sobre transcripciones truncadas a 60k chars muestreadas uniformemente (una casa ocupada nunca se ve entera) → decisiones de dinero sobre una conjetura. "Conversaciones hoy" y "tiempo de respuesta" son correctos pero solos no dicen qué hacer.
- **Bueno**: tiempo de respuesta p50, el precio F3 determinista, las coordenadas validadas.

Resumen: los KPIs actuales son más **medición que decisión**. Faltan métricas que respondan "¿qué hago ahora?" y "¿está Sara ganando o perdiendo dinero?".

### Set propuesto (ordenado por prioridad/impacto)

1. **Rendimiento de Sara (cobertura, cierre, seguridad).**
   - *Decisión*: ¿subir más números a AUTO o frenar? ¿Sara cierra tan bien como un humano?
   - *Datos*: YA capturados (`agent_generated`, `agent_status` paused_risk/paused_human, escalaciones, acks de copiloto) → **solo SQL**.
   - *Métricas*: % conversaciones tocadas por Sara, cierre Sara vs humano, tasa de pausa-por-seguridad, tasa de takeover (humano interviene), dónde pierde al cliente.

2. **Funnel real en SQL (escriben → preguntan precio → cotizado → reserva).**
   - *Decisión*: dónde se cae el cliente; qué casa convierte peor.
   - *Datos*: "escriben" y "preguntan precio" son SQL-computables; mantener la IA **solo** para el cierre blando y los ingresos.
   - *Vive en*: tope del funnel en SQL en `worker.py`; tile + informe.

3. **Comparación entre números/casas (`wa_comparison`).**
   - *Decisión*: qué línea/casa rinde mejor (convs, conv_rate, p50, avg).
   - *Datos*: YA existen por fila de análisis con `wa_number_id` → `GROUP BY wa_number_id`.

   - *Datos*: `list_followup_candidates` ya define el predicado; falta exponerlo (ver UX) y agregarlo (count + valor estimado).
   - *Vive en*: chip en `chats.html` + tile "Presupuestos sin cerrar" en dashboard.

5. **Tiempo de primera respuesta por modo (AUTO vs humano).**
   - *Decisión*: ¿Sara mejora el tiempo de respuesta lo suficiente para justificar el riesgo de ban?
   - *Datos*: ya tenemos timestamps + `agent_generated` → SQL.
   - *Vive en*: tile comparativo + informe.

6. **Salud anti-ban (envíos vs topes, días con Redis caído).**

   - *Datos*: contadores de `rate_limit` + log de "redis-error"/fail-open (hay que capturar/persistir el evento de fail-open — hoy solo se loggea).
