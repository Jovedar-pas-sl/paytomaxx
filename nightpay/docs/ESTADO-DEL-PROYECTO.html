1. Qué es NightPay

Plataforma de cobros para venues nocturnos en España. El cliente paga con su móvil escaneando un QR (sin app instalada). La chica/operadora crea cada cobro, el sistema toma un 10% de comisión automático, y el 90% se acumula como saldo pendiente para ella. El admin paga sus comisiones en USDT (cripto) porque la mayoría son LatAm con solo pasaporte y los bancos españoles no las aceptan.

Phase 1B añadió modo prepago: el cliente carga un saldo UNA vez al entrar (como una pulsera de hotel all-inclusive) y la chica consume contra ese saldo durante la noche sin volver a molestarlo.

Ejemplo simplificado de una noche

  1. Cliente A llega al venue, paga 500€ vía QR → wallet creado "Mesa 3".
  2. Durante la noche, Ana le cobra 8€ (cervezas), 100€ (habitación),

200€ (tiempo con ella). Cliente nunca vuelve a sacar el móvil.

  1. Ana acumula 90% de 200€ = 180€ de comisión instant.
  2. Cliente A se va. Admin refunda 192€ a su tarjeta original.
  3. Final del mes, admin paga a Ana sus 180€ × N noches → envío en USDT a

su Binance. Tronscan verifica auto → MATCHED.

3. Foundation

Multi-tenant + RLS

Cada operación lleva un tenantId (UUID del venue). El middleware Prisma inyecta WHERE tenantId = current automático en cada query. Row-Level Security habilitado a nivel Postgres como defensa en profundidad: aunque alguien se cuele a la DB con el role de la app, no puede leer datos de otro venue sin el contexto correcto.

Ejemplo: tenant isolation

-- Si un atacante con JWT de venue "luna-vlc" intenta consultar pagos de
-- "luna-mad" haciendo SQL directo:

SELECT * FROM payments WHERE id = '<uuid de luna-mad>';
-- → 0 rows (la RLS policy lo filtra invisible)

-- Sin el current_tenant_id seteado:
RESET app.current_tenant_id;
SELECT * FROM payments;
-- → 0 rows (RLS deny por default)

Auth + roles

JWT con issuer=nightpay, audience=nightpay-internal. Roles jerárquicos: OWNER (dueño) → MANAGER (encargado) → WAITER (camarero) → OPERATOR (chica).

Ejemplo: protección anti brute-force

Un atacante prueba 5 passwords incorrectos contra ana@local.test. Al 5º intento, Redis guarda nightpay:lockout:locked:ana@local.test con TTL 15 min. La 6ª llamada con CUALQUIER password (incluso el correcto) devuelve 403 Account locked, try in 14 min.

Adicionalmente, rate-limit IP: si la misma IP hace >10 logins en 60s, Redis bucket por bucket devuelve 429 Retry-After: 30s.

4. Cobros — 3 modos

NightPay soporta 3 modos de captura que la chica elige por cobro:

ModocaptureMethodQuién procesa el dineroCuándo usarlo
QR clienteQR (default)PSP de NightPay (Wipay/Peanpe)Cliente paga desde su móvil escaneando el QR
WalletWALLET_TOPUPPSP de NightPay (top-up) + consumos internosCliente carga saldo UNA vez al entrar (Phase 1B)
DatáfonoPOS_EXTERNALPSP del bar (Redsys/SumUp del datáfono físico)Cliente paga con tarjeta física en el datáfono del bar

La chica decide por cada cobro qué modo usa con un toggle en su app.

4a. Modo QR (cliente paga con su móvil)

Flow del modelo clásico (sin wallet):

  1. Chica → operator app → introduce 50€ → terminal del venue.
  2. API crea Payment(status=CREATED) + qrToken único + TTL 5 min.
  3. La chica enseña el QR a la pantalla del cliente.
  4. Cliente escanea → /pay/<qrToken> → ve detalles → paga.
  5. Web-client llama a /start-authorization → API redirige al PSP.
  6. Cliente confirma con su banco → PSP envía webhook a /v1/webhooks/<provider>.
  7. API valida HMAC + idempotencia + FSM transition → AUTHORIZED.
  8. Hook auto: crea OperatorEarning con snapshot de su commissionBps.
  9. WebSocket emite payment:completed → chica ve "✓ Cobrado".

Ejemplo: cobro real

23:47 — Cliente pide una copa, Ana en operator app:

  1. Inicio → "Crear cobro" → 12€ → enseña QR.
  2. Cliente escanea con su Android → web-client carga en 800ms → "Pagar".
  3. Wipay redirige al banco del cliente → cliente firma con biometría.
  4. Banco aprueba → Wipay POST webhook a NightPay con HMAC válido.
  5. API: Payment fce4... → AUTHORIZED. Hook crea OperatorEarning:

- paymentAmountCents: 1200 - commissionBps: 9000 (snapshot — si OWNER cambia el % después, este earning queda con 90%) - commissionCents: 1080

  1. WebSocket payment:completed → operator app muestra "✓ +10.80€".

Total elapsed: ~6 segundos del QR a "cobrado". El cliente no nota el roundtrip al PSP — solo ve la pantalla de su banco como pago normal.

FSM completa

CREATED ──→ AWAITING_CAPTURE ──→ AUTHORIZING ──→ AUTHORIZED
   │                                  │
   │                                  ├──→ FAILED
   │                                  ├──→ EXPIRED
   └─────────────────────────────────→ CANCELED

Cada transición se valida con applyEvent() (XState 5). Si alguien intenta mover un Payment ya AUTHORIZED a otro estado, tira InvalidTransitionError.

4b. Modo Datáfono (cobro POS_EXTERNAL)

Cuándo importa: muchos venues ya tienen un datáfono físico del bar (Redsys, SumUp Air, iZettle, etc.) — el cliente prefiere pagar con su tarjeta física insertándola en un datáfono real. El dinero pasa por el PSP del bar, NO por NightPay. Pero la chica sigue queriendo su comisión.

Flow:

  1. Chica → operator app → toggle "Datáfono" → introduce 50€ → "Generar cobro POS".
  2. NightPay crea un Payment con captureMethod=POS_EXTERNAL, status=CREATED,

TTL 30 min (más que QR normal porque el camarero camina).

  1. La pantalla de la chica muestra el importe grande + código corto verbal

(ej. "#A4F7E2") + instrucciones "Llama al camarero".

  1. Chica llama al camarero. Le pasa el código verbalmente: "50€, código A4F7E2".
  2. Camarero llega con el datáfono del bar.
  3. Cliente paga 50€ con su tarjeta física en el datáfono — el PSP del bar

procesa la transacción y aprueba.

  1. Camarero abre su operator app (tiene rol WAITER) → tab POS → ve la

lista de cobros pendientes → toca el cobro "#A4F7E2 — 50€ — Ana".

  1. Camarero opcionalmente pega el nº de recibo del datáfono → click

"Confirmar pagado".

  1. NightPay marca Payment AUTHORIZED vía FSM event POS_CONFIRMED

(transición directa CREATED → AUTHORIZED, sin AUTHORIZING porque no hay PSP roundtrip).

  1. El hook estándar crea OperatorEarning para la chica con su

commissionBps. WebSocket le notifica → ella ve "✓ Cobrado" instant.

Importante:

  • El dinero pasa por el PSP del bar, no por NightPay. NightPay solo

registra la transacción para repartir comisión a la chica.

  • La chica NO se autoconfirma sus propios cobros POS (anti auto-confirm).

Debe ser otro role (WAITER/MANAGER/OWNER).

  • Si el camarero tarda >30 min o nunca confirma, el cron de QR-expiration

marca el Payment como EXPIRED. La chica puede cancelar manualmente antes.

Ejemplo: cobro POS en un viernes noche

23:50 — Cliente A pide la cuenta del rato con Ana. Total: 80€.

Ana → operator app → toggle "Datáfono" → 80€ → "Generar cobro POS". Pantalla muestra: 80,00 EUR — #A4F7E2 — Llama al camarero.

Ana llama a José (camarero). "Mesa 3, 80€, código A4F7E2".

José coge el datáfono Redsys del bar → introduce 80€ → cliente A inserta su tarjeta → PIN → "APROBADO" → tickets impresos. El datáfono mandará el settlement al banco del bar como siempre.

José → operator app → tab POS → ve "#A4F7E2 80€ Ana hace 1 min" → toca → "Confirmar pagado en el datáfono". Apunta el nº recibo del Redsys "047215" → click Confirmar.

NightPay backend:

  • FSM: CREATED → AUTHORIZED via POS_CONFIRMED { posReceiptRef: "047215" }
  • Crea `OperatorEarning(paymentId=p-xyz, paymentAmountCents=8000,

commissionBps=9000, commissionCents=7200)`

  • Audit log: payment.pos_confirmed por José (WAITER)
  • WebSocket → Ana ve "✓ Cobrado +72€" en su app.

Cliente A se va con el ticket del Redsys del bar (no de NightPay). El bar settlea sus 80€ vía su PSP normal. Ana acumula 72€ en saldo pendiente para su payout mensual.

Reconciliación: el dinero del cobro POS no aparece en NightPay (no gestiona el flow). El admin debe cuadrar al final del mes los totales del datáfono del bar vs la suma de OperatorEarning.paymentAmountCents con captureMethod=POS_EXTERNAL que NightPay registró. Si cuadran, todo OK. Si no, alguien confirmó algo sin cobrar o vice versa.

Restricciones de seguridad

La chica NO puede tocar campos financieros:

  • commissionBps (su %)
  • active (dar de baja)
  • payoutMetadata (datos extra del banco)

Eso queda OWNER-only en el admin. La validación está en el Zod schema + en el guard del endpoint.

8. Phase 1B — Wallet cash-in-advance

Por qué existe

Regla #1: no molestar al cliente. En el modelo clásico, cada vez que la chica quería cobrar algo le pedía el móvil al cliente para escanear su QR de pago. Pésima UX en un venue nocturno donde el cliente está bebiendo, hablando, etc.

Con wallet, el cliente paga UNA vez al entrar (un cargo en su tarjeta, descriptor neutro tipo "SERVICIOS LV MADRID") y durante la noche la chica le cobra sin tocarlo.

Legal — closed-loop prepaid

Operado bajo EMD2 art. 1.5(k): closed-loop prepaid exemption. El saldo:

  • Solo se gasta dentro del venue
  • No se convierte en cash directamente
  • Refund solo a la tarjeta original

Mismo modelo legal que casinos con chips de plástico, parques de atracciones con pulseras RFID, hoteles all-inclusive. No requiere licencia EMI.

9. Comisiones configurables

Venue.platformCommissionBps (default 1000 = 10% NightPay / 90% chica). Venue.operatorMaxCobroCents (cap por cobro creado por OPERATOR, default 200€). Ambos editables desde admin → tab Ajustes (OWNER-only).

Ejemplo: cálculo en bps

Ana tiene commissionBps=9000 (90%).

Cliente paga 50€ (5000 céntimos).

  • Comisión chica: floor(5000 × 9000 / 10000) = 4500 céntimos = 45€.
  • Comisión NightPay: 5000 - 4500 = 500 céntimos = 5€.

OWNER decide bajar a Ana al 80% (commissionBps=8000). Los earnings ya existentes mantienen su 90% (snapshot). Los nuevos cobros que haga Ana usarán 80%.

14. Decisiones de diseño

Multi-tenant con RLS hard-enforced

Doble defensa: middleware Prisma + RLS Postgres. Si alguien se cuela en la DB con el role de la app, no puede leer cross-tenant.

Adapter pattern para pasarelas

Cada pasarela implementa GatewayAdapter. Añadir Stripe o Mollie = escribir un nuevo adapter, sin tocar el resto del código.

FSM para pagos con XState 5

Los pagos tienen muchos estados. XState formaliza las transiciones legales. applyEvent() valida o tira InvalidTransitionError.

Earnings con snapshot de bps

Cuando una chica cobra y va AUTHORIZED, su comisión se persiste con un snapshot del bps actual. Si OWNER cambia el % después, los earnings históricos no se reescriben.

Idempotency keys obligatorios

Tanto en POST /payments como en POST /wallets/:id/consume. El camarero puede pulsar 2 veces "Cobrar" sin generar 2 cobros.

Closed-loop prepaid = sin licencia EMI

Phase 1B opera bajo EMD2 art. 1.5(k). Saldo solo se gasta dentro del venue, sin conversión a cash, refund solo a la tarjeta original. Mismo modelo legal que casinos con chips.

Phase 1C SoftPOS descartada

Se evaluó tap-to-phone con Viva.com / SumUp. Se descartó por complejidad operativa (KYB con otro PSP, hardware Android NFC, certificación). QR clásico + wallet prepago cubren el caso.

15. Riesgos abiertos

AML banco español

Pattern "PSP settlement → SEPA outgoing a Binance" puede generar review. Mitigación: ratio sano (no 100% a cripto), contabilidad clara, chicas dadas de alta como autónomas / con factura.

Fiscalidad chicas

Si residen >183 días en España, ingresos USDT son rendimiento gravable. Modelo 100 + Modelo 721 si saldo cripto >50k€ a 31/dic. Responsabilidad de cada chica, NO de NightPay, pero éticamente conviene avisarles.

MCC vs operativa real

El registro hostelero (5813/5812/7011) debe coincidir con la operativa. Si se registra como hostelería pero la operativa real difiere, el PSP eventualmente detecta (review periódico, denuncia, redes) → cierre cuenta. Mitigación: fachada y operativa coherentes.

Travel Rule cripto

Binance pide info del receptor para envíos >1.000€ a self-custody. Entre cuentas Binance es trivial. Para self-custody (Trust Wallet) preparar los datos.

Chargebacks

Por ahora ningún cliente nos ha hecho chargeback porque no hay tráfico real. Cuando lleguen, el PSP retiene del settlement. Mitigación: tracking de disputas + fondo de reserva.
